# Tech Sales — требования (допрос)

Ответы фиксируются по мере опроса.

---

## 1. Бизнес и роль системы

### 1.1. Это B2C (розница), B2B (опт/дилеры) или оба?
**Ответ:** B2C. Желательна бонусно-реферальная программа.

### 1.2. Кто вы в цепочке: перекуп с витриной, маркетплейс нескольких поставщиков, или свой склад + подтягивание цен с каналов?
**Ответ:** Перекуп с витриной (закуп у поставщиков под заказ / под наличие).

### 1.3. География: РФ / СНГ / другое? Есть ограничения по доставке?
**Ответ:** Только РФ. Москва — самовывоз; регионы — СДЭК.

### 1.4. Ассортимент: смартфоны, ноутбуки, бытовая техника, всё подряд? Нужна ли жёсткая категоризация?
**Ответ:** Нужна жёсткая категоризация. Ассортимент на старте:
- все смартфоны;
- вся техника Apple (все категории и виды);
- Samsung;
- Dyson;
- Sony PlayStation;
- Ray-Ban;
- Oculus.

### 1.5. Бренд/название магазина уже есть?
**Ответ:** White Shop.

## 2. Telegram-каналы поставщиков

### 2.1. Каналы открытые, закрытые, или и то и другое? Сколько примерно каналов на старте?
**Ответ:** И открытые, и закрытые. На старте 10+ каналов. Парсинг — с активной Telegram-сессии (user/MTProto), не через Bot API.

### 2.2. Формат постов: один товар = один пост? прайс-листы текстом/фото/PDF/Excel?
**Ответ:** Прайс-листы текстом в одном посте + PDF / Excel.

### 2.3. Нужен парсинг картинок/скриншотов (OCR) или только текст?
**Ответ:** В MVP хватит текста (+ PDF/Excel из 2.2). OCR картинок не нужен. В каналах может быть несколько сообщений с разными категориями товаров.

### 2.4. Как сопоставлять один и тот же товар у разных поставщиков? Ручная модерация, правила, ИИ?
**Ответ:** В идеале комбо: ИИ/правила предлагают → админ подтверждает.

### 2.5. Что делать при конфликте цен/наличия у нескольких поставщиков: брать мин. цену, приоритет поставщика, показывать оба?
**Ответ:** На витрине — медиана цен по поставщикам + наценка. (Одна витринная цена, не несколько предложений.)

### 2.6. Как часто обновлять: realtime / каждые N минут / по событию?
**Ответ:** По расписанию каждые 15 минут (посты часто редактируются, поэтому не чистый realtime).

### 2.7. Нужен ли лог «откуда взялась цена» (канал, пост, время) для админа?
**Ответ:** Да.

## 3. Ценообразование и витрина

### 3.1. Наценка: фиксированный %, разные % по категориям/брендам/поставщикам, формула?
**Ответ:** Базово — фиксированный %. Систему заложить гибко: несколько стратегий наценки (фикс %, по категориям/брендам и т.п.), чтобы менять без переделки.

### 3.2. Округлять цены (до 10/100 ₽)? Показывать «старую» цену / скидки?
**Ответ:** Округление до 100 ₽. Скидки и зачёркнутая «старая» цена не нужны.

### 3.3. Показывать ли остатки: «в наличии / под заказ / срок N дней»?
**Ответ:** Не показывать наличие — только цена и кнопка заказа.

### 3.4. Если товар исчез из каналов — сразу снимать с витрины или держать N часов/дней?
**Ответ:** Сразу снимать с витрины.

### 3.5. Нужны ли ручные товары (свои позиции без Telegram)?
**Ответ:** Да. Также ручной раздел HOT — горячие товары по хорошей цене.

## 4. Заказы и исполнение

### 4.1. После заказа: вы сами закупаете у поставщика, или заказ уходит поставщику автоматически?
**Ответ:** Менеджер вручную закупает у поставщика.

### 4.2. Статусы заказа: какие нужны?
**Ответ:**
- Клиенту: оформлен → оплачен → отменён / готов к выдаче → выдан.
- Админу: принят → оплачен → обработан → собран → отгружен.

### 4.3. Доставка: СДЭК / самовывоз / другое на старте?
**Ответ:** Только то, что в 1.3: Москва — самовывоз, регионы — СДЭК. Больше на старте не нужно.

### 4.4. Нужны ли возвраты, частичные отмены, замена модели?
**Ответ:** На старте не нужны. После оформления заказа менеджер связывается с клиентом, всё подтверждает и принимает оплату сам.

### 4.5. Что если после заказа цена у поставщика выросла / товар пропал?
**Ответ:** Гибрид: при небольшой разнице — фиксируем цену заказа и несём разницу сами; при существенной — менеджер связывается с клиентом (новая цена / отмена / аналог). Порог разницы — на усмотрение менеджера / настраиваемый позже.

## 5. Оплата

### 5.1. Какие способы оплаты? Онлайн-эквайринг нужен сразу или оплата только через менеджера?
**Ответ:** Только через менеджера (перевод/наличные/как скажет). Онлайн-эквайринг на старте не нужен.

### 5.2. Чеки / 54-ФЗ / онлайн-касса нужны сразу?
**Ответ:** На старте без фискализации.

## 6. Личный кабинет пользователя

### 6.1. Регистрация: телефон + SMS, Telegram Login, email/пароль, или только через Telegram?
**Ответ:** Telegram Login + email/пароль. Персональные данные обрабатывать аккуратно по закону (152-ФЗ и т.п.: согласия, политика, минимизация данных).

### 6.2. Что в ЛК: заказы, адреса, избранное, уведомления, история просмотров, бонусы?
**Ответ:** Заказы и статусы; избранное; уведомления; история просмотров; бонусы и рефералка; профиль. Адреса доставки в ЛК на старте не нужны.

### 6.3. Детали бонусно-реферальной программы?
**Ответ:** Трёхуровневая реферальная система с регулируемым % кэшбэка на внутренний счёт в системе.

### 6.4. Роли кроме покупателя: менеджер, админ, поставщик?
**Ответ:** На старте только админ (полный доступ). Отдельные роли менеджера/модератора/поставщика — позже при необходимости.

## 7. Клиенты: сайт, Mini App, iOS, Android

### 7.1. Что в MVP обязательно, а что можно отложить?
**Ответ:** Приоритет: 1) Telegram Mini App → 2) сайт → 3) админка (web) → 4) iOS → 5) Android.

### 7.2. Mini App = полноценный магазин или урезанный?
**Ответ:** Как сайт — тот же функционал.

### 7.3. Нативные iOS/Android или кроссплатформ? Предпочтение?
**Ответ:** Flutter.

### 7.4. Нужны пуши: статус заказа, падение цены, «товар снова в наличии»?
**Ответ:** Нужны: смена статуса заказа; падение цены на избранное; товар снова появился; сообщения менеджера / рефералка.

### 7.5. Общий дизайн/брендбук есть, или с нуля?
**Ответ:** Только логотип (монограмма W+A+S, ч/б). Брендбук нет — визуал с нуля на базе лого. Файл: `assets/logo-white-shop.png`.

## 8. Админка

### 8.1. Что критично админу на старте?
**Ответ:** Обязательно: каналы поставщиков; сырой парсинг / очередь модерации матчинга; каталог и карточки; наценки / стратегии цен / HOT; заказы; пользователи и бонусы/рефералка; лог происхождения цен. Аналитика (продажи, маржа) — не в первой версии (можно позже).

### 8.2. Нужна ли «песочница»: сначала парсим → админ подтверждает → на витрину?
**Ответ:** Автопубликация. Товаров слишком много — всё вручную не отсмотреть. (Уточнение к 2.4: ИИ/правила матчат автоматически; админ вмешивается точечно при ошибках, не подтверждает каждую позицию.)

### 8.3. Уведомления админу в Telegram о новых заказах / ошибках парсинга?
**Ответ:** Да: новые заказы; ошибки парсинга; подозрительный матчинг / резкий скачок цен.

## 11. Выбранный стек (решение)

Приоритеты: **производительность** (быстрый API, быстрый каталог, фоновые джобы без блокировок) и **оперативность** (быстро развивать, один язык на бэке+парсере, один web-клиент на сайт/Mini App/админку).

### Решение

| Слой | Технология | Зачем |
|------|------------|--------|
| API | **Python 3.12 + FastAPI** | Async, высокая скорость ответов, тот же язык что и парсер |
| Worker / парсер | **Telethon** + фоновые задачи (**ARQ** на Redis) | Лучшая экосистема MTProto user-session; PDF/Excel/ИИ-матчинг удобнее в Python |
| БД | **PostgreSQL 16** | Каталог, заказы, рефералка, лог цен; JSONB для сырых постов |
| Кэш / очереди | **Redis 7** | Кэш витрины, сессии, очередь джобов каждые 15 мин |
| Поиск каталога | **PostgreSQL full-text** на старте → при росте **Meilisearch** | Оперативно сейчас; легко ускорить поиск позже |
| Web + Mini App + Admin | **Next.js (TypeScript) + React** | Один код: сайт, Telegram Mini App, админка (роли/роуты) |
| Mobile | **Flutter** | Уже зафиксировано; общий REST/JSON API |
| Auth | JWT + Telegram Login Widget / Mini App `initData` + email/password | Как в 6.1 |
| Файлы | локальный volume / S3-совместимое позже | PDF прайсов, медиа |
| Инфра | **Docker Compose** → VPS; на сервере опционально **Xray VLESS Reality** → `TELEGRAM_PROXY=socks5://xray:1080` | Сейчас за границей — без VPN |
| ИИ-матчинг | LLM API (нормализация названий) + правила/словари | Автопубликация; админ правит исключения |

### Почему не другое

- **Go API + Python worker** — чуть выше потолок RPS, но два языка замедляют оперативность на старте; при вашем объёме (10+ каналов, 15 мин) FastAPI не будет узким местом.
- **NestJS/Node everywhere** — слабее Telethon и парсинг PDF/Excel; для MTProto-сессии Python надёжнее.
- **Отдельный фронт на Vite без Next** — хуже SEO витрины; Mini App всё равно web, Next закрывает оба режима.
- **Отдельные админка/магазин** — лишняя поддержка; один Next.js с `/admin`, `/` и mini-app shell.

### Монорепо (план структуры)

```
tech-sales/
  apps/
    api/          # FastAPI
    worker/       # Telethon + ARQ jobs
    web/          # Next.js: store + mini-app + admin
    mobile/       # Flutter (позже)
  packages/
    shared/       # общие типы/контракты (по необходимости)
  docker-compose.yml
  REQUIREMENTS.md
  assets/
```

### Производительность на практике

- Витрина: денормализованные карточки + Redis-кэш медианы/цен; пересчёт в worker, не в HTTP-запросе.
- Парсинг: инкрементально по каналам каждые 15 мин, без блокировки API.
- API: async FastAPI, connection pool к Postgres, пагинация каталога.
- Клиент: Flutter/Next ходят в один API; тяжёлая логика не на клиенте.
